# 项目宪法（Project Constitution）

> 本文档为项目的**最高指导原则**，所有技术决策、代码变更、架构演进必须遵循本宪法的核心条款。未经团队核心成员评审，不得随意修改。


## 序言

我们致力于构建**可维护、可测试、可演进**的前端应用。在快速交付与长期质量之间，我们选择**有质量的速度**。本宪法旨在为团队提供清晰的决策依据，减少分歧，提升协作效率。


## 第一章：技术主权

### 第一条 技术选型原则

- **稳定性优先**：核心依赖库须为 LTS 版本或拥有明确维护承诺的稳定版本
- **最小依赖原则**：新增依赖须评估必要性、包体积、维护活跃度
- **渐进式升级**：框架升级须有明确收益，不盲目追新

### 第二条 技术栈锁定

本项目技术栈锁定如下，非经架构评审不得变更：

| 领域 | 技术选型 | 版本要求 |
|------|---------|---------|
| 前端框架 | Vue 3 | ≥ 3.4.x |
| 编程语言 | TypeScript | ≥ 5.0.x |
| 构建工具 | Vite | ≥ 5.0.x |
| 状态管理 | Pinia | 最新稳定版 |
| 包管理器 | pnpm | ≥ 8.0.x |
| HTTP 客户端 | Axios（统一封装） | 最新稳定版 |
| 代码规范 | Airbnb JS Style + Vue 3 适配 | — |


## 第二章：架构法则

### 第三条 分层架构（不可违背）

代码必须遵循 **单向依赖** 的四层架构：

```
app/（入口层） → pages/（页面层） → features/（业务层） → shared/（基础层）
```

- **铁律一**：基础层（`shared/`）不得引用任何上层模块
- **铁律二**：业务层（`features/`）之间不得互相引用
- **铁律三**：页面层（`pages/`）只做组装，不得包含业务逻辑
- **铁律四**：越界引用一律视为架构违规，ESLint 检查不通过即阻塞合并

### 第四条 关注点分离

- **UI 与逻辑分离**：业务逻辑必须封装在 `hooks/` 或组合式函数中，组件只负责渲染和事件分发
- **状态管理边界**：全局状态用 Pinia（`stores/`），模块局部状态用 `provide/inject` 或组合式函数
- **副作用隔离**：API 请求、定时器、事件监听等副作用统一在组合式函数或 `onMounted` 中管理


## 第三章：代码质量

### 第五条 类型安全（强制）

- **零 `any` 容忍**：除极特殊情况（须注释说明 + 团队评审），禁止使用 `any`
- **全量类型覆盖**：所有函数、组件 Props、API 响应须明确定义类型
- **严格模式**：`tsconfig.json` 须开启 `strict: true`

### 第六条 可测试性

- 核心工具函数（`shared/lib/`）必须有单元测试，覆盖率目标 ≥ 80%
- 业务组合式函数（`features/*/hooks/`）应有单元测试或集成测试
- 关键用户路径应有 E2E 测试（视项目规模决定）

### 第七条 代码量约束

| 维度 | 上限 | 说明 |
|------|------|------|
| 单文件组件 `<script>` 部分 | ≤ 300 行 | 不含 template 和 style |
| 组合式函数 | ≤ 200 行 | 超过即拆分 |
| 单函数 | ≤ 50 行 | 保持单一职责 |
| 单文件工具函数 | ≤ 500 行 | 超过即按领域拆分文件 |


## 第四章：安全与合规

### 第八条 安全基线

- **禁止硬编码**：密钥、密码、Token、API 密钥等敏感信息必须通过环境变量注入
- **输入净化**：所有用户输入须经过校验或转义，防范 XSS
- **依赖审计**：定期执行 `pnpm audit`，高危漏洞须在 48 小时内修复

### 第九条 环境变量治理

- 所有环境变量必须在 `shared/config/env.ts` 中统一声明和校验
- 缺失环境变量必须在构建阶段报错，不得延迟到运行时


## 第五章：协作流程

### 第十条 变更流程

| 变更类型 | 流程要求 |
|---------|---------|
| 日常功能开发 | 遵守规范 → 自测 → 提交 PR → Code Review → 合并 |
| 架构调整 | 先出 RFC 文档 → 团队评审 → 分阶段实施 |
| 依赖升级（Major） | 评估影响 → 团队评审 → 制定回滚方案 → 执行 |
| 重构 | 小步快跑，每步有测试验证，不搞“大爆炸式”重构 |

### 第十一条 审查门槛

- **每个 PR 必须通过**：TypeScript 编译、ESLint 检查、单元测试
- **Code Review 关注**：架构合规性、类型安全、性能敏感点、安全风险
- **禁止自审自合**：至少一名团队成员的批准方可合并


## 第六章：治理与演进

### 第十二条 宪法权威

- 本宪法优先级高于所有个人偏好和第三方规范
- 若第三方规范（如 Airbnb 风格指南）与本宪法冲突，以本宪法为准
- 所有自动化工具（ESLint、Prettier、TypeScript）的配置须与宪法条款保持一致

### 第十三条 修订机制

- 任何成员可提出修订提案，须附理由说明和影响评估
- 修订须经团队评审，**共识达成**后方可生效
- 重大修订（涉及架构、技术栈）须有 **迁移计划** 方可执行
- 每次修订须更新版本号并记录变更日志
